==== Zimt Memory Tagging

Zimt is not ratified, and UDB does not define it yet, so its tests are built only for a configuration whose `test_config.yaml` lists Zimt under `experimental_extensions`, which also enables experimental extensions as `ENABLE_EXPERIMENTAL_EXTENSIONS` does.
Zimt takes its instructions from Zimop: `gentag`, `addtag` and `checktag` are MOP.RR.1 encodings and `settag` is a MOP.RR.0 encoding.
The suite has one group per privilege mode: Zimt_Sm, Zimt_S, Zimt_U and Zimt_H (VS-mode and VU-mode).
Each group covers the instructions with memory tagging disabled, the MT_MODE fields and tag generation exclusion mask CSRs, the software-check exception in the delegation and cause CSRs, `gentag`, `addtag`, `settag` and `checktag` with memory tagging enabled, and the implicit tag checks of loads and stores.
The `settag` and `checktag` tests store and check tags in the tag table of each mode, which needs Svatag (S, U, VS and VU modes) or Smvatag (M-mode), and pointer masking of that mode to ignore the pointer tags in the address.
They check every tag byte and half byte around the tags; the store/AMO page faults, guest-page faults and access faults of tag stores, including the one of tag storage in memory that is not idempotent; the masked address of `rs1`, sign-extended with address translation and zero-extended without; and, with `mstatus.MPRV`, the tag table of the current privilege with the pointer masking and translation of the effective one.
The `checktag` tests check the range of chunks that it compares and the software-check exception of a mismatch, and the load page faults, guest-page faults and access faults of tag loads.
Without first-stage address translation, the scalar loads and stores of data, other than those that use `sp` as the base register, are tag checked: the tests cover each kind of load and store, integer, floating-point and compressed (Zca, Zcb, Zcd), the `sp`-relative ones and `checktag` with `sp`, misaligned ones over two chunks, of which no part may be performed when a chunk mismatches, the access faults of tag loads before those of the data, a memory tag with bit 7 set, `mstatus.MPRV` (also with `MPV`), the order of the tag checks after the hart's own tag stores and `settag`, the accesses that are not checked (LR/SC, AMOs, CMOs and vector loads and stores), and the software-check exceptions that `hedeleg` delegates to VS-mode.
With first-stage address translation (`satp`, `vsatp`), only the pages whose leaf PTE has PTE.MTAG and X = 0 are tagged-data pages: the tests check them, pages without PTE.MTAG, pages with it and X = 1 (tagcheck-exempt code pages), the user pages that S-mode accesses, which it does not check, and those of U-mode and VU-mode, through `mstatus.MPRV`, loads and stores over two pages, also into an unmapped page, whose fault comes first, the loads and stores of the instructions of tagcheck-exempt code pages, which are not checked, also of execute-only ones, of VS-stage ones and for an instruction over two code pages, and PTE.MTAG in non-leaf and G-stage PTEs, where it is reserved, and with memory tagging disabled, which ignores it; with the G stage only (`vsatp` Bare) all pages are tagged-data pages, and the tag loads can raise load guest-page faults.
`HLV` and `HSV` are checked with the memory tagging and tag table of their guest mode, which `hstatus.SPVP` selects (VU-mode's is `senvcfg.MT_MODE` in HS-mode and `hstatus.VUMT_MODE` in HU-mode), with two-stage translation in VS-stage tagged-data pages only, and their mismatch sets GVA, unless `hstatus.MTAG_I` is set, and `HLVX` never; with `mstatus.MPRV`, `mstatus.MTAG_I` makes loads and stores unchecked, and neither `mstatus.MTAG_I` without `MPRV` nor `hstatus.MTAG_I` makes those of S-mode, VS-mode and VU-mode unchecked.
A trap that writes a nonzero `mtinst` or `htinst` deposits the PTE.MTAG bit of the code page of the trapping instruction in `mstatus.MTAG_I` or `hstatus.MTAG_I`: the tests take the guest-page fault of an implicit access of a VS-stage walk, whose `htinst` must hold a pseudoinstruction, from a VS-stage tagcheck-exempt code page and from another one, and no other such trap while they use `MTAG_I` or a tagcheck-exempt code page, as whether other traps write a nonzero value is implementation-defined.
The M-mode trap handler runs with M-mode's memory tagging, and reads the trapping instruction of S-mode with `mstatus.MPRV`, so the M-mode tests, and the S-mode ones without address translation, raise no exception with memory tagging enabled, but for those with `mstatus.MTAG_I` set, which M-mode takes, and the M-mode tests check mismatches with `mstatus.MPRV`.
The parts of the S-mode and HS-mode tests that run in M-mode and take its traps (`mstatus.MTAG_I` without `MPRV`, `MPRV` with `MPP` = U and `MPV`) need standard M-mode (`STANDARD_SM_SUPPORTED`), and their coverpoints are in the Sm covergroup, which a certificate without Sm drops.
Misaligned loads and stores over two chunks are tested in those modes only with `UDB_MISALIGNED_LDST`, as they trap otherwise, and over two pages only with misaligned accesses performed byte by byte (`MISALIGNED_SPLIT_STRATEGY` = sequential_bytes).
The access-fault cases need `RVMODEL_ACCESS_FAULT_ADDRESS_STORE` and `RVMODEL_ACCESS_FAULT_ADDRESS_LOAD`, and exist only if the DUT defines them.
With Smstateen, `mstateen0.MT` gates the S-level and H-level CSRs of Zimt and Svatag below M-mode, and with Ssstateen `hstateen0.MT` the S-level ones in VS-mode: Zimt_Sm_stateen (which needs S-mode and Smstateen) checks both bits (including that `hstateen0.MT` reads 0 once `mstateen0.MT` is cleared while it is 1) and, in each of their states, the access to the CSRs from M, S, U, VS and VU modes, which raises an illegal or virtual instruction exception or reaches the CSR. The boot code sets both bits with Zimt, as it sets those of the other state, for the other tests. As the test sets the bits from M-mode, its covergroup is that of M-mode (Zimt_Sm_cg): a certification without M-mode (EXCLUDE_SM) does not cover the gating, and no test covers `hstateen0.MT` on a hart with Ssstateen but not Smstateen, for which the specification makes VS-mode raise the virtual instruction exception whenever `hstateen0.MT` = 0.
With Sdtrig, Zimt_Sm_trigger checks, with `mstatus.MPRV` and S-mode's memory tagging, so that M-mode takes the exceptions with its own memory tagging disabled, that a load or store address breakpoint of M-mode that fires before the access (the timing that the Debug specification suggests, which the test assumes, as the Sdtrig tests do) has priority over the tag check of loads, stores, LR/SC, AMOs, `cbo.zero` and vector loads, and that the tag loads of the check never match triggers. No Sargantana configuration has Sdtrig, so it runs on `sail-rv64-gcbhv-zimt`.
The specification does not allocate the CSR addresses, the PTE.MTAG bit and the MT bit of `mstateen0` and `hstateen0` yet: the tests use the placeholders of the Sail model (PTE.MTAG is bit 58, MT bit 53).
4-bit pointer tags are mandatory and 7-bit ones optional: a configuration that supports them sets `ZIMT_POINTER_TAG_WIDTH_7` under `experimental_params`, and the cases and bins that need them exist only then.
The VITT ranges of M-mode (Smvatag) and of a mode with Bare first-stage address translation (Svatag), whose loads, stores and `settag` raise access faults, are implementation-defined: the tests whose loads, stores or `settag` run with memory tagging enabled there take them as empty, and exist only without the extension or for a configuration that sets `SMVATAG_NO_M_MODE_VITT_RANGE` or `SVATAG_NO_BARE_VITT_RANGE` under `experimental_params`, as do the bins that only they cover: the `_mt` tests and the `settag` and `checktag` tests of M-mode and of Bare translation, also through `mstatus.MPRV` and with the G stage only.

==== Svatag Supervisor Tag Table Bases

Svatag is not ratified, and UDB does not define it yet, so its tests are built only for a configuration whose `test_config.yaml` lists Svatag under `experimental_extensions`, which also enables experimental extensions as `ENABLE_EXPERIMENTAL_EXTENSIONS` does.
It defines the tag table base CSRs of S, U, VS and VU modes, for the Zimt tag accesses.
The tests cover the CSRs' WARL behavior and their access from each mode, including the VS-mode access to `svitts` and `svittu`, which reaches `vsvitts` and `vsvittu`; Zimt_Sm_stateen checks that `mstateen0.MT` and `hstateen0.MT` gate that access.
The Zimt `settag` and `checktag` tests check which tag table each mode uses, and the tag table protection with first-stage address translation, at the edges of the VITT ranges: the loads and stores and `settag` of S-mode, U-mode, VS-mode and VU-mode (U-mode and VU-mode from a user alias of the code region), those of U-mode, VS-mode and VU-mode through `mstatus.MPRV`, and HLV and HSV, also in HU-mode, with pointer tags, whose tag check comes first, and with memory tagging disabled, or HLVX, which it does not protect (Zimt_S_checktag, Zimt_H_checktag).
Svatag depends on Svukte, which a configuration that lists Svatag must implement too (the framework stops otherwise), and assumes the even split of the address space that Svukte enforces: with `senvcfg.UKTE` (`hstatus.HUKTE` for HLV in HU-mode), the tag accesses of U-mode and VU-mode (`settag`, `checktag` and the implicit checks, also through `mstatus.MPRV` and HLV) raise page faults at a tag address in the upper half, so their tag table must be in the lower half (Zimt_S_checktag, Zimt_H_checktag).
